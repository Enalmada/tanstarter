# Security

- **CSP.** A per-request nonce and a strict policy are set by `createCspMiddleware` in `src/start.ts`. Allow a new third-party origin in `src/config/cspRules.ts`, not with `unsafe-inline` or `unsafe-eval`. Inline scripts must go through `ScriptOnce`, which applies the nonce.
- **CSRF.** Server functions are called with the session cookie, so `createCsrfMiddleware` (wired to server-function requests in `src/start.ts`) rejects cross-site calls. better-auth checks the origin on `/api/auth` itself. Make every state-changing server function a `POST`, and do not add a state-changing GET route.
- **Server functions.** Each needs `authMiddleware` or `freshAuthMiddleware`, except the few public ones listed in `src/functions/__tests__/auth-wiring.test.ts` (session probe, locale cookie, role self-service flag); adding one means adding it to that list on purpose. Row-level access on the entity CRUD goes through CASL rather than role string comparisons. See [Auth](auth.md).
- **Environment.** Server secrets are declared in `env.config.ts` and never leave the server. Only `APP_ENV` and the keys in `PUBLIC_RUNTIME_ENV_KEYS` (`src/lib/env/public-env.ts`) are copied into the page, from an explicit allowlist. Adding a key there publishes it to every visitor. `bun run check-client-leaks` checks the client bundle for server-only code.
- **Redirects.** User-supplied redirect targets go through `safeRedirect`.
- **Wire payloads.** The global error translator returns only a safe message. Never attach `cause`, stack traces or row data to an error that reaches the client; the serializer would send it.
- **Logs and errors.** Metadata only. Error reports are sanitized before they leave (`src/lib/monitoring/sanitize.ts`): ORM "Failed query" messages carry bound values.
- **Secrets in git.** Betterleaks scans the commits of a branch: `bun run scan:secrets` locally (errors until Betterleaks is installed; the pre-commit hook only warns and skips) and in CI (`secret-scan.yml`). Use credential-free example URLs. A reviewed false positive is either an inline `betterleaks:allow` comment or a fingerprint in `.betterleaksignore`.
- **Static analysis.** Semgrep (`.github/workflows/semgrep.yml`) scans `src`, `scripts`, the Dockerfile and `fly.toml`. A pull request fails only on findings it adds; the weekly run scans everything. The rulesets are fetched from the Semgrep registry at run time, so a rule change can pass or fail a pull request without a diff here. Silence a reviewed false positive with `// nosemgrep: <rule id> (<reason>)`, and skip code that is not ours in `.semgrepignore`. The secret scan also plants a token in a throwaway repo on every run, so a scanner that has stopped detecting anything fails the job instead of passing quietly.
- **CI supply chain.** Every action in `.github/workflows/` is pinned to a commit SHA with its version in a trailing comment, and every workflow sets `permissions: contents: read` (widen it per job, never at the top). Dependabot (`.github/dependabot.yml`) raises the weekly updates for actions and the Docker base image. When adding an action, pin the SHA of a release tag; never `@main`, `@master` or a floating major.
- **Repository settings** (not in the repo, so check them after a fork): a ruleset on `main` that requires a pull request, the required status checks and no force pushes; GitHub secret scanning with push protection; Dependabot security updates; private vulnerability reporting (`SECURITY.md` sends reporters to it); two-factor authentication required for the GitHub org, Fly.io and the database host. `.github/CODEOWNERS` only takes effect once the ruleset requires code-owner review, and GitHub ignores an author's own approval, so the maintainer's own pull requests on those paths need a second owner or a bypass. Replace `@Enalmada` in CODEOWNERS with your own handle or team. Do not filter a workflow on `paths:` at the trigger if it may become a required check: a pull request that matches none of the paths gets no check-run and waits on it forever. Semgrep, the dependency audit, the container scan and the Storybook tests start on every pull request for this reason (Storybook decides in a `changes` job instead, and a job skipped by `if:` satisfies a required check).
- **Container.** The Docker base image is pinned by digest and Dependabot keeps it current. The runner stage also applies Debian security updates at build time, which trades bit-for-bit reproducible images for fixes; the digest still fixes the base. `container-scan.yml` builds the image and fails on a fixable CRITICAL (Trivy). A reviewed exception goes in `.trivyignore` as `CVE-... exp:YYYY-MM-DD` with the reason on the line above, so it lapses on its own. Fly checks `/health` before sending traffic to a Machine (`fly.toml`).
- **Dependencies.** `bun run audit:deps` runs on every pull request and weekly (`dependency-audit.yml`): it fails on a high or critical advisory in production dependencies, or a critical one anywhere. A newly published advisory therefore fails every open pull request until it is cleared, which is why it is worth requiring: fix it once on `main`. Clear findings with `bun audit fix`; use a `package.json` `overrides` entry only for a transitive copy that a dependent's range blocks, and record in the pull request when it can be removed (the `seroval` override can go once the TanStack devtools stop pinning the 1.5 line). `bunfig.toml` holds new package versions back for a few days before install. Do not add an exemption to get a fresh release unless the maintainer asks.
